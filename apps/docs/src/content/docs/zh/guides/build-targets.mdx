## 框架目标与 CSS 目标

Adapter 只有 `weapp` 与 `web` 两个 CSS target，它们与框架的平台名不是同一层概念。

| 框架构建 | 平台环境 | 示例中的 Panda 目录 | Adapter target |
| --- | --- | --- | --- |
| Taro 微信 | `TARO_ENV=weapp` | `styled-system/weapp` | `weapp` |
| Taro H5 配置 | `TARO_ENV=h5` | `styled-system/h5` | `web` |
| Uni-app 微信 | `UNI_PLATFORM=mp-weixin` | `styled-system/mp-weixin` | `weapp` |
| Uni-app H5 | `UNI_PLATFORM=h5` | `styled-system/h5` | `web` |
| Weapp Vite + Wevu 示例 | `weapp.platform: 'weapp'` | `styled-system` | `weapp` |
| React Web 示例 | Vite Web 构建 | `styled-system` | `web` |

仓库 Taro 产物测试覆盖微信，Uni-app 覆盖微信与 H5。框架具备某个脚本，或 CSS 选择 `weapp`，都不能证明所有平台已验收。详见[框架支持矩阵](/zh/frameworks/)。

## 平台必须先于 codegen 设置

Panda 在框架构建开始前读取配置。如果平台变量仅由后面的框架命令设置，前面的 `panda codegen` 进程读取不到它。

仓库[平台 runner](https://github.com/weapp-pandacss/weapp-pandacss/blob/main/examples/run-platform.mjs)先设置 `TARO_ENV` 或 `UNI_PLATFORM`，再依次运行 Panda 与框架，并传入同一环境。在仓库根目录使用示例脚本：

~~~sh
pnpm --filter @weapp-pandacss/taro-app build:weapp
pnpm --filter @weapp-pandacss/taro-app build:h5
pnpm --filter @weapp-pandacss/uni-app-vue3 build
pnpm --filter @weapp-pandacss/uni-app-vue3 build:h5
~~~

自己的 runner 也应将平台同时传给两个进程，不要靠“最近构建的是哪个目标”推断 runtime 目录。

## 每个目标使用独立产物

Taro 的 Panda 配置可以按平台选择目录，同时保持源码导入不变：

~~~ts
// panda.config.ts
import process from 'node:process'
import { defineConfig } from '@pandacss/dev'
import { weappPanda } from 'weapp-pandacss/panda'

const platform = process.env.TARO_ENV || 'weapp'

export default defineConfig({
  plugins: [weappPanda()],
  polyfill: false,
  presets: ['@pandacss/preset-base', '@pandacss/preset-panda'],
  include: ['./src/**/*.{js,jsx,ts,tsx}'],
  preflight: platform === 'h5',
  outdir: 'styled-system/' + platform,
  importMap: 'styled-system',
  outExtension: 'mjs',
  forceImportExtension: true,
  jsxFramework: 'react',
})
~~~

Taro Vue 扫描需要加入 `.vue` 并采用对应的 Vue 编写配置；Uni-app 使用 `UNI_PLATFORM || 'mp-weixin'` 与 `jsxFramework: 'vue'`。请按完整[框架示例](/zh/frameworks/)接入，不要用这段配置替换所有框架设置。

以下项目需要对齐：

| 设置 | 职责 |
| --- | --- |
| Panda `outdir` | 当前进程写入 runtime 与类型产物的位置 |
| Panda `importMap` | 提取器识别的逻辑导入 |
| Bundler `styled-system` alias | 当前目标构建时的 runtime 解析目录 |
| TypeScript `styled-system/*` paths | 编辑器与类型检查读取声明的位置 |
| 框架输出目录 | 当前目标最终应用产物的位置 |

Taro/Uni 示例的 TypeScript paths 指向默认小程序目录，bundler alias 按平台选择 runtime 目录。目标具有不同生成类型约定时，还需提供对应 TypeScript 配置。编辑器能解析类型，不代表 bundler 使用了同一产物。

仅当生成目录与最终输出目录都独立时，不同目标才能并行构建。即使编码相同，也不要让两个进程写同一个 `outdir`。Web/H5 保留 `target: 'web'` 的 adapter，切换目标无需旧式 runtime rollback。

## 工作目录与 watch

Panda 按自己的工作目录解析文件。Wevu Vite 配置显式设置 Panda PostCSS cwd，因为 mpcore/Vitest 等 API 构建会保留工作区根目录作为进程 cwd：

~~~ts
import panda from '@pandacss/dev/postcss'

const pandaPlugin = panda({ cwd: import.meta.dirname })
~~~

应传入实际应用目录，不要让无关的 Panda 配置共用一个不明确的根目录。

示例流程先执行初始 codegen，再启动框架 dev/watch。Panda PostCSS 会记录提取依赖，让 bundler 能重建样式。独立流程需要监视 runtime 生成时，Panda 2.1.2 也提供 `panda codegen --watch`，CSS 仍需要经过 PostCSS。每个生成目录指定一个写入负责人。

修改 recipe、token、`include` 或 hash 后，确认 runtime 与 CSS 都已重新生成。环境、alias、TypeScript 配置变化可能需要重启框架进程。保留生成标记能让重复处理安全，但不能让并发写入安全。

## 缓存与干净构建

缓存 key 应包含 target、Panda/adapter 版本与 Panda 配置，只恢复该目标的生成与框架输出目录。Web 缓存覆盖小程序 runtime 后，导入路径看似有效，也可能指向错误的生成结果。

恢复时先停止写入受影响目标的进程，清理该目标的生成/输出缓存，再重新生成和构建。不要删除另一个运行中目标的文件。完成后比较实际节点 class 与样式，而不只是接受 codegen 成功。

## Panda 与 Tailwind 入口隔离

Uni-app 对比示例分别维护入口：

~~~text
panda.css → 虚拟 CSS 入口内的 Panda PostCSS → Panda adapter → rem/单位转换
tailwind.css → weapp-tailwindcss 专用流程 → 与它配套的 class runtime
~~~

Panda 入口提前展开，因为 Tailwind generator 可能在框架 PostCSS 运行前删除仅含 layer 顺序声明的输入。虚拟入口会将 Panda dependency 消息登记为 Vite watch 依赖。

示例 [panda-postcss.cjs](https://github.com/weapp-pandacss/weapp-pandacss/blob/main/examples/uni-app-vue3/panda-postcss.cjs)跳过 `tailwind.css`，仅适配 Panda 与手写 CSS；`WeappTailwindcss` 显式接收 Tailwind `cssEntries`。不要再注册第二个 Tailwind generator，也不要把其已适配 CSS 送进 Panda 编码器。这是示例集成方式，不是 adapter 新选项。

## 按目标验收

对实际支持的每个目标验证干净构建、源码编辑、recipe/配置编辑与重启，检查别名、输出位置、selector/class 匹配与 token 声明。Web 还需验证浏览器样式和交互，小程序需在选定 IDE 或设备验证。仅产物匹配不能证明渲染效果或所有框架交互。
