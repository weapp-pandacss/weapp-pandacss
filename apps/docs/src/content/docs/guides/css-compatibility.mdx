## What the target changes

Both targets encode class names. `target: 'web'` then retains native CSS layers and selectors. The default `weapp` target also performs platform selector conversion and layer-order compilation.

This adapts a stylesheet's syntax and order. It does not add a CSS engine, make every property available in WXSS or guarantee identical behavior across mini-program renderers and base libraries.

## Normal layer order

Keep `polyfill: false` in Panda configuration so the adapter receives original layers. By default, `cascadeLayers.mode` is `ordered`, using `@weapp-tailwindcss/css-compat@0.1.1` through a compatibility adapter. Public configuration and class naming do not change. The compiler registers layers at their first declaration and emits rules in layer order even if their blocks appear in a different order.

~~~css
.probe { color: green; }
@layer base, utilities;
@layer utilities { .probe { color: blue; } }
@layer base { .probe { color: red; } }
~~~

For this equal-specificity case, the output rule order is:

~~~css
/* Naming marker omitted from this excerpt. */
.probe { color: red; }
.probe { color: blue; }
.probe { color: green; }
~~~

The unlayered normal declaration is emitted last. Named, repeated, dotted, nested and anonymous layers are handled; same-layer source order is preserved.

## Important declarations reverse the order

For important declarations, earlier layers have higher priority and unlayered important declarations have lower priority:

~~~css
@layer base, utilities;
@layer base { .probe { color: red !important; } }
@layer utilities { .probe { color: blue !important; } }
.probe { color: green !important; }
~~~

The emitted important-rule order is green → blue → red, so red wins in this equal-specificity case. Rules with both normal and important declarations may be split to preserve the two different orders.

| Declaration kind | Emission order, lower priority first |
| --- | --- |
| Normal | earlier layer → later layer → unlayered |
| Important | unlayered → later layer → earlier layer |

The repository tests cover these orders and the nested layer rules. Browser tests compare safe fixtures against native layers. The Wevu example also includes two interactive layer probes.

## Specificity is a compatibility boundary

Ordered compilation is **order compatibility**, not a complete native layer polyfill. WXSS still resolves ordinary selector specificity after layers have been removed.

~~~css
@layer base, utilities;
@layer base { #card .probe { color: red; } }
@layer utilities { .probe { color: blue; } }
~~~

Native layers let the higher-priority utilities layer win. After flattening, `#card .probe` can win on specificity despite appearing first. The adapter emits `WP_LAYER_SPECIFICITY`; the browser regression deliberately preserves and checks this difference.

Prefer comparable class-selector specificity across layers. Refactor the high-specificity rule or its component styling interface rather than adding a specificity placeholder. Use strict diagnostics where a potential difference should block a build:

~~~js
// postcss.config.cjs
module.exports = {
  plugins: {
    'postcss-import': {},
    '@pandacss/dev/postcss': {},
    'weapp-pandacss/postcss': {
      cascadeLayers: { mode: 'ordered', onConflict: 'error' },
    },
  },
}
~~~

The default `onConflict: 'warning'` reports risks through PostCSS warnings with layer, selector, property and source location. A warning is conservative; it does not prove both selectors match the same element. Shorthand, logical properties and unknown selector functions need conservative analysis.

## Imports are supported in source CSS

Expand the **complete import graph** before Panda generation and ordered compilation. The adapter consumes one CSS AST and does not load imported files. Ordinary imports matter too: imported unlayered styles can override every normal layered rule, and layer-qualified imports register their place in the layer order.

~~~css
/* src/app.css */
@import "./base.css";
@layer utilities { .probe { color: blue; } }
~~~

~~~css
/* src/base.css */
.probe { color: red; }
~~~

Native CSS selects red because it is unlayered. Simply retaining the import and removing the local layer can incorrectly select blue. With [the complete PostCSS pipeline](/postcss/), the importer merges both files first, then ordered compilation emits blue before red so red still wins. The same rule applies when an imported file imports another file.

| Import scenario | Required handling |
| --- | --- |
| Local plain, named/anonymous layer, media or supports imports | Expand first; preserve layer and condition metadata for ordered compilation |
| Multiple files contributing to one layer | Combine their graph into one root before adaptation; same-layer fallback order remains source order |
| Duplicate or cyclic local imports | Follow the importer's deduplication semantics; do not depend on repeating a file to create a new cascade |
| File missing, malformed or misplaced import | Fix the importer/parser error at its source; do not drop the rule |
| Remote import left by `postcss-import` | Vendor locally or fully resolve upstream; a residual remote import fails with `LAYER_IMPORT` |
| Imported file changes during watch | Reprocess its entry; custom/virtual loaders must forward dependency messages and watch the imported files |
| Independently compiled component or subpackage CSS | Each root has its own layer order; share application CSS only where component isolation permits it |

This check concerns **source imports entering ordered compilation**. A framework can later generate valid WXSS `@import` rules to load independently compiled assets, such as Uni-app's separate Tailwind stylesheet; those output dependencies do not enter the Panda layer root.

Pass the real entry filename as PostCSS `from`, especially when a build starts from another working directory. If you call Panda on a virtual entry, expand imports from the real entry first; resolving `./base.css` from a virtual URL or the process directory can select the wrong file. Do not delete imports, fetch files inside the layer core or copy already-flattened CSS back into the source graph to bypass the check.

## Conditional layers and one-root ordering

Declare the complete layer order outside conditions before using it inside `@media` or `@supports`:

~~~css
@layer base, utilities;
@layer base { .probe { color: red; } }
@media (min-width: 700px) {
  @layer utilities { .probe { color: blue; } }
}
~~~

The compiler keeps conditional wrappers. A first conditional declaration may produce `WP_LAYER_CONDITIONAL_ORDER` because registration can differ from native CSS.

Sorting covers **one PostCSS root**. Separately compiled files and isolated component styles do not share a global layer registry. If rules need one cross-file order, combine their input before the adapter. Import and nesting expansion must run earlier. Loading several independently flattened files later does not reconstruct the lost layer information.

## Selector differences

These default transformations are covered by selector tests:

| Source selector | Mini-program output |
| --- | --- |
| `:root` or `:host` | `page` |
| `*` | `view,text` |
| `.container * > text` | `.container view>text,.container text>text` |
| `.container :where(.a, .b) > text` | `.container .a>text,.container .b>text` |
| `* ~ *` | `view+view,view+text,text+view,text+text` |
| `.a:not(.disabled)` | Handwritten negation retained |

`:where()` expansion no longer has native zero specificity. Universal replacement only includes the configured tags, by default `view` and `text`. The `~` conversion shown above changes general siblings to adjacent siblings; it is not a general sibling polyfill. `:is()` is handled by the csstools plugin with `isPseudoClassPluginOptions`.

Use native tags and selectors that your renderer supports. A retained pseudo-class does not establish native interaction support: Web hover is tested in the React example; mini-program touch states should follow the component/framework's supported state mechanism. Root and universal replacement can be configured through [PostCSS options](/postcss/).

## Diagnostic fixes

| Diagnostic or rejected input | Fix |
| --- | --- |
| `WP_LAYER_SPECIFICITY` | Make cross-layer specificity comparable; verify the actual cascade, or fail with `onConflict: 'error'` |
| `WP_LAYER_CONDITIONAL_ORDER` | Declare named layer order before conditions; avoid relying on condition-dependent registration |
| `WP_LAYER_SELECTOR_UNKNOWN` | Replace the unknown function with supported selectors or explicitly inspect the affected cascade |
| Generated `:not(#\#)` placeholders | Disable Panda polyfill and regenerate from original layers |
| `LAYER_IMPORT`: any residual `@import`, plain, layer-qualified or remote | Expand the full graph before ordered compilation; remote imports need a separate upstream resolver or local source |
| CSS nesting / `&` selectors | Expand nesting in an earlier stage |
| `revert-layer` | Rewrite the rule explicitly; layer rollback cannot be reproduced after flattening |
| `LAYER_NAME`: invalid layer names or unsupported declarations | Correct the layer declaration at the reported source position |
| `LAYER_PREPROCESSOR`: remaining conditional-compilation control comments | Consume `#if` / `#else` / `#endif` directives before the adapter |
| `LAYER_DESCRIPTOR_ORDER` / `LAYER_WRAPPER_SEMANTICS` | Review descriptor order or wrapper semantics; strict mode promotes these compatibility warnings to errors |

The three `WP_LAYER_*` names above remain text prefixes for compatibility. Machine-readable warnings use `LAYER_SPECIFICITY`, `LAYER_CONDITIONAL_ORDER` and `LAYER_SELECTOR_UNKNOWN`; all core warnings include `diagnostic` and source positions. `onConflict` affects compatibility warnings, not invalid input: residual imports, nesting and `revert-layer` fail even in warning mode. See [the full diagnostic reference](/api/postcss-plugin/#layer-order-and-diagnostics).

Malformed selectors and invalid mini-program variable names also throw errors. Variable declarations, `var()` references and `@property` names must use ASCII identifiers or generated Panda tokens.

## Explicit legacy mode

Old options such as `removeNegationPseudoClass`, `selectorReplacement.cascadeLayers` and `cascadeLayersPluginOptions` select the legacy path when explicitly supplied, even if the value equals an old default. You can also choose `cascadeLayers: { mode: 'legacy' }`.

Do not combine these options with an explicit `mode: 'ordered'`: that is a configuration error. Legacy does not guarantee native layer semantics either. Web always retains native layers. See the [migration guide](/migration/) before carrying old configuration forward.
